# Entropy Service v2.8.0 — certificate tools and Windows service setup

v2.8.0 adds browser-local certificate generation, an optional Windows server
service in the bundled installer, clearer upgrade progress and desktop access
to the web application. It also refines adaptive HTTP acquisition and makes
LAB support and profiling controls clearer across Linux, Windows and macOS.

## Certificate tools for local services and TLS experiments

Open `/api-certificates.html` from the server homepage to create a self-signed
TLS server certificate and matching ECDSA P-256 private key. Useful applications
include local HTTPS bootstrap, separate identities for LAB peers, IPv4/IPv6 and
private-DNS client tests, certificate pinning and preparing a replacement
identity before deployment.

- Configure 1–32 DNS/IP subject alternative names and 1–365 days of validity.
  Defaults are seven days with `localhost`, `127.0.0.1` and `::1`.
- Review the names, UTC validity and SHA-256 fingerprint. Download the public
  certificate and unencrypted PKCS#8 private key separately; only the public
  certificate is displayed in the page.
- Key generation combines exactly 64 same-origin server bytes with 64 independent
  browser CSPRNG bytes using HKDF-SHA-256. Both inputs affect the private key;
  an unavailable or malformed entropy response stops generation.
- Private scalar multiplication and ECDSA signing use native Web Crypto. A
  Firefox compatibility path uses native ECDH and public-only point
  decompression, accepting a public point only when exactly one candidate
  verifies a native signature. JavaScript does not perform private scalar
  multiplication or convert private scalars to BigInt.
- Private material is not uploaded, placed in URLs or persisted in browser
  storage by this implementation. Clear/navigation drops page references and
  cancellation discards late results. Downloads remain on disk, and browser
  memory does not guarantee secure erasure.

Use a trusted HTTPS origin or local loopback HTTP. The result is a self-signed
server leaf, not a CA or a publicly trusted identity. The page does not install
files, change trust stores, restart a server or replace its current identity.
Deployment, private-file permissions, certificate renewal and client trust
remain explicit operator tasks. Server output follows its configured source
and reseed policy; combining inputs does not certify additional entropy.

The [certificate guide](https://github.com/fantuz/entropy-service/blob/v2.8.0/docs/certificate-bootstrap-design.md)
includes Linux, Windows and macOS examples, the native-provider design and trust
limits. The local `entropy-server generate-cert` command remains available for
installation before any server is running; installers do not depend on the
browser page.

## Windows installer: visible upgrades and an optional server service

The bundled GUI setup keeps desktop installation available without elevation
and now offers an administrative **all-users** mode. **Install entropy-server
as a Windows Service** is off by default, with a separate, also unchecked
**Start the server service after installation** option. entropy-client remains
a desktop/CLI application.

The optional `EntropyServer` service uses `NT SERVICE\EntropyServer`, automatic
delayed startup and loopback HTTP/HTTPS on ports 8080/8443. On first start it
provisions a seven-day self-signed certificate under protected
`C:\ProgramData\entropy-service`; renewal is manual. It does not change the
firewall or trust stores.

First service installation requires a new directory directly inside Program
Files, without directory links. Setup rejects adopting an existing desktop-only
installation for a privileged service. Existing installer-managed services
support in-place upgrades: setup stops them gracefully, retains configuration
and identity, and resumes them if previously running or explicitly requested.
Uninstall removes only the owned service registration and retains state,
certificates and logs. Switching current-user/all-users modes requires an
explicit uninstall and fresh installation; separate user data is retained.

Upgrade preparation and old-runtime cleanup now display an animated progress
indicator and a count of removed files/folders. Cleanup processes Windows
messages, handles read-only files and does not traverse directory junctions.
File failures produce an actionable error. The licence display reflows
paragraphs without changing the installed MIT `LICENSE`.

README, homepage and installer include the credit:

> Software Architecture, Build Pipelines and Security Audit by Massimiliano Fantuzzi

The installer remains unsigned. See the
[Windows installer guide](https://github.com/fantuz/entropy-service/blob/v2.8.0/docs/windows-gui-installer.md)
for installation modes, upgrade boundaries, service ownership and retained files.
HTTPS certificates do not provide Authenticode installer signing.

## Desktop access, LAB availability and profiling

Both desktop views now offer **Open web application** on Linux, Windows and
macOS. It opens the selected server's homepage in the default browser only on
request, converting HTTP/WebSocket endpoints to their corresponding web origin
and discarding API paths, queries and fragments. Invalid or credential-bearing
endpoints are rejected. The browser uses its own certificate trust settings;
the GUI's health CA file does not install browser trust.

Server GUI shortcuts make LAB source settings and the existing debug listener
more discoverable. The options editor scrolls focused controls into view. LAB
pages remain embedded on all supported server builds; an empty registry does
not disable browser inputs or network tools. The source catalog reports the
running platform and supported registration kinds. Unsupported direct-device
registrations are rejected on macOS as well as Windows.

The [LAB platform matrix](https://github.com/fantuz/entropy-service/blob/v2.8.0/docs/lab-platforms.md)
distinguishes browser capabilities from server-side transports: HTTP/WebSocket,
TCP and UDP are shared; Unix-domain sockets are available on Linux/macOS;
direct devices use the Linux reader. Network cameras need external FFmpeg.
Physical audio, camera and RNG operation still requires device qualification.

Profiling works across all three operating systems with explicit `-debug=true`
and remains off by default. Its separate loopback listener is
`http://127.0.0.1:6060/debug/pprof/`; `/debug` on the main web port is not that
listener. GUI controls apply to the next GUI-owned run, not a separately
monitored process.

## Adaptive acquisition and HTTP request budgets

Optional adaptive pull now backs off by **33%**, or to the larger measured
workload target, subject to the configured ceiling. After **eight consecutive**
healthy observations, recovery reduces the interval by **50%**, bounded by the
measured target and requested refresh. Fixed pacing remains the default;
adaptive mode does not change payloads, analysis settings or server failure
policy.

The client exposes a separate `-request-timeout` setting, also available in GUI
Options. The established default remains **three seconds**; explicit values
from **1 ms to 30 seconds** support larger samples or slower links, and `0`
selects the default. Adaptive pacing does not extend request deadlines.
Cancellation and the overall run duration may stop a request earlier.

For example, on Linux with the public certificate obtained through a trusted
channel:

```sh
SSL_CERT_FILE=/absolute/path/entropy-server-cert.pem \
  entropy-client -mode=pull -url=https://localhost:8443/v1/data/random \
  -slice=33554432 -refresh=100ms -adaptive -request-timeout=15s
```

A larger deadline accommodates transfer/generation time; it does not guarantee
that a backend or connection can sustain a requested frame rate. See the
[client performance guide](https://github.com/fantuz/entropy-service/blob/v2.8.0/docs/client-capabilities-performance.md).

## Validation and documentation

Regression coverage includes native certificate generation in Chromium and
Firefox, private-key downloads kept outside uploaded evidence, malformed entropy
and cancellation, and a real Go TLS listener with an independently verifying
client. Certificate tests also check self-signatures, matching keys, SANs,
validity, usage, entropy-input sensitivity and native-provider failure bounds.

Installer qualification covers upgrade from the released v2.6.0 installer,
responsive cleanup, file/link ownership, installed GTK operation and the
optional administrative service lifecycle. GUI tests exercise LAB settings,
the real pprof listener and web-origin selection. Large-sample qualification
uses explicit acquisition budgets rather than treating shared-runner throughput
as a payload-size limit. Full release CI retains the existing quality, race,
fuzz, vulnerability, browser, native-platform, endurance and container checks.
These checks do not establish a cryptographic audit or physical-device support.

Public guides now describe current controls and platform limits, with fresh
running GUI screenshots. Historical measurement evidence and command examples
are retained; no new cross-platform throughput or coverage percentage is claimed.
