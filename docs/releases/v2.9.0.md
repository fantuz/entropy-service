# Entropy Service v2.9.0 — smaller WebSocket previews and desktop backend discovery

The byte viewer can now display an 8 MiB sample with a **292-byte WebSocket message**. Applications that consume complete samples can keep their current format. On the desktop, the server and client GUIs read backend choices directly from the selected executable.

## WebSocket and browser changes

- The byte viewer requests `format=preview` on `/bytes`. The preview is also available on `/colors`. Each binary message contains the generated byte count, the SHA-256 digest of the entire sample and up to 256 leading bytes. At 20 updates per second, previews of an 8 MiB sample carry 5,840 application bytes/s. The server still generates, accounts for and hashes the full sample. Use `format=compact` when you need the digest and every generated byte. [WebSocket formats](https://github.com/fantuz/entropy-service/blob/v2.9.0/docs/api.md#websockets)
- The default WebSocket JSON encoder streams the hexadecimal and Base64 fields. On a Linux amd64 benchmark with an 8 MiB input, allocation fell from 71,601,736 to 35,296 bytes per message. Median time to receive the complete JSON message over loopback fell from 63.1 to 37.1 ms. The measurement includes the same 27,962,125-byte payload in both versions. [Benchmark setup and results](https://github.com/fantuz/entropy-service/blob/v2.9.0/docs/runtime-review-v2.8.1.md)
- The status dashboard pauses polling in the background and refreshes when the tab becomes visible or the browser restores the page. It preserves the exact text of large counters and reads each Prometheus scrape once.

## Desktop and CLI changes

- Run `entropy-server -describe-json` to see which generators the build includes and whether the CPU supports RDRAND when compiled in. Run `entropy-client -describe-json` to inspect acquisition modes and platform-specific export destinations. Both commands work without starting a listener or contacting a server. [Configuration reference](https://github.com/fantuz/entropy-service/blob/v2.9.0/docs/configuration.md)
- The server GUI lists usable generators from the selected binary and exposes HTTP and WebSocket concurrency and memory limits. The client GUI reads acquisition modes from its executable, respects the adaptive-pull setting and displays the most recent throughput measurement. The GUI retains a fallback for older companion binaries. [Desktop guide](https://github.com/fantuz/entropy-service/blob/v2.9.0/docs/desktop-gui.md)

## RDRAND measurements and build changes

A repeatable benchmark measures how long the server takes to record new seed material while native RDRAND reads hold the shared freshness lock. On an AMD EPYC KVM guest with four concurrent 32 MiB reads, the 99th percentile ranged from **155 to 208 ms** across three runs of 100 trials. Timing starts with seed bytes already in memory. Physical hardware qualification remains open. [Method, results and reproduction command](https://github.com/fantuz/entropy-service/blob/v2.9.0/docs/experimental-rdrand.md#reseed-latency-during-concurrent-reads)

The Go build cache now tracks assembly source changes. Installer language checks run on warm caches, and CI avoids recompressing already packaged macOS, Windows and OCI artifacts. The client test for interrupted JSONL output now observes a partial write before cancelling, so it exercises the same condition on slower runners.
