# Entropy Service v2.5.0 — experimental CPU output and resilient publication

This release adds opt-in direct RDRAND output for CPU/VM experiments, improves
container publication resilience, and includes the parallel CI and release
maintenance updates since v2.4.1. Existing software defaults remain AES-256-CTR
or ChaCha20 according to the target architecture.

## Experimental direct CPU backend

Select `-drbg=rdrand-experimental` on native x64 builds with advertised RDRAND
support, including Linux and Windows. The server GUI offers the same option;
existing HTTP/WebSocket clients can consume its output. Unsupported targets and
`purego` builds reject selection explicitly.

- Output consists of direct CPU words, without application-owned deterministic
  software child streams. CPU, firmware and hypervisor trust apply. This is not
  raw sensor output or an independently certified entropy source.
- External source reads retain the existing startup/freshness admission policy,
  but do not seed or condition CPU output. Existing CPU seed mixing remains a
  separate feature.
- Each word permits one attempt plus ten retries. A failed read is cleared and
  stops serving-root generation across connections until restart, including
  when reseed failure policy is `continue`. There is no silent software fallback.
- Startup probes, mode headers, readiness JSON and a distinct backend-failure
  counter identify operation and failures. Bounded instruction attempts do not
  provide a hard wall-clock deadline.

The [guide](https://github.com/fantuz/entropy-service/blob/v2.5.0/docs/experimental-rdrand.md)
contains Linux/Windows examples, cancellation boundaries, trust limitations and
raw benchmark evidence. On one virtualized AMD EPYC host, direct CPU output
measured about 308–316 MB/s and 3.32 ms per MiB, with zero allocations per read.
AES/ChaCha20 were faster; alternating pinned comparisons showed no clear
software-backend slowdown. These are host-specific generation measurements,
not network-rate guarantees or physical CPU qualification.

## Container publication and CI

- Retry recognized transient GHCR failures, including `unknown blob`, with at
  most four attempts and 2/4/8-second backoff. Registry commands have bounded
  attempt timeouts. Permanent authentication/content errors and exhausted
  retries still fail visibly.
- Upload and verify all six server/client platform images and SBOM attachments
  before updating either consumer-facing index. Pin platform references by
  digest, compare remote configs with the exact tested image, and verify final
  index membership. Final writes to two repositories remain separate operations.
- Recheck the current stable release after the final `latest` write so a slow
  registry retry cannot finish successfully against a newly superseded release.
- Linux quality, race, fuzz and terminal validation run independently in
  parallel. Workload-specific caches and explicit aggregate gates retain full
  PR reporting. Pure-Go CPU selection tests run on Linux and Windows.
- Relative GUI artifact paths and a real GoReleaser checksum regression protect
  native/installer release integration. Controlled publication recovery retains
  exact tagged source and already-tested artifact validation.

Focused fault tests cover transient recovery, retry exhaustion, timeout limits,
permanent-error rejection, failed client staging, remote config mismatch,
untested index members and stable-release changes during the last write.
Full tagged CI must pass before publication, including Go/race/lint/vet,
vulnerability checks, fuzzing, Chromium/Firefox, Linux/Windows GTK, packaged
Windows Service, endurance, three container platforms and isolated installer
installation/uninstallation.

The per-user installer includes both GUI views, both Go utilities and private
Python/GTK libraries; no separate Go/Python/MSYS2 installation is needed. Open
**Entropy Server** and **Entropy Client** from the Start menu. The server shortcut
starts with loopback HTTP for initial testing; configure HTTPS/certificates for
remote use. The installer remains unsigned; Authenticode signing is deferred.
See the [installer guide](https://github.com/fantuz/entropy-service/blob/v2.5.0/docs/windows-gui-installer.md).

architecture-specific `releases/latest/download` aliases continue to work.
