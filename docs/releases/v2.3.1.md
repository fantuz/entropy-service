# Entropy Service v2.3.1 — containers, readiness and reliable builds

This maintenance release adds multi-architecture container distribution, readiness checks and image maintenance, and makes client retry/export tests reliable across Linux and Windows. Existing command-line, web and desktop features are retained.

## Highlights

- **Server and client containers:** separate `ghcr.io/fantuz/entropy-service` and `ghcr.io/fantuz/entropy-client` images for Linux amd64, arm64 and ARMv7. Images use digest-pinned bases, run without root, support a read-only root filesystem and include system CA roots and licensing notices. The server includes the web interface and LABs.
- **Stable delivery:** versioned release tags and a moving `latest` stable channel complement the validated `edge` development channel. Publication promotes the exact tested image archives without rebuilding. Serialized `latest` promotion resolves the current stable GitHub release, validates both image indexes and all six application identities, and copies by digest. Older backfills reconcile the current stable release.
- **Readiness without extra shell tools:** the server image includes `entropy-health`, with bounded requests, HTTP status checks and verified HTTPS/custom public CA support. Compose defaults to the stable channel and waits for a healthy server before starting the optional client.
- **Image maintenance:** final-image vulnerability scans and SPDX SBOMs cover all three architectures. Fixable HIGH/CRITICAL findings and invalid scan reports block publication. SBOMs are attached to platform image digests as OCI referrers; complete reports are retained in CI for 90 days. Weekly scans refresh evidence for stable and development images, and Dependabot proposes base-image and Actions updates.
- **More reliable client tests:** retry/export checks account for buffered HTTP reception. A deterministic regression verifies an exact 600-byte capture, its summary and cancellation of an additional request already in flight. The same timing assumption was removed from truncated-response coverage; exact payload and retry-budget checks remain.
- **Clearer project presentation:** refreshed README status badges and live Linux desktop GUI, Source LAB and Socket LAB screenshots. GitHub Actions updates cover checkout, Go/Python setup, GoReleaser and Quantis evidence uploads. `VERSION` now records the intended release, and tagged publication checks that it matches.

## Deployment and compatibility

- Container images run Linux, including Docker Desktop's Linux-container mode. Native Windows distribution remains an x64 portable archive.
- The container quick start uses OS seeding and loopback-published HTTP. Configure HTTPS or an appropriate TLS reverse proxy for remote deployment. Private/self-signed identities need explicit client trust. See the [container guide](https://github.com/fantuz/entropy-service/blob/v2.3.1/docs/containers.md) for TLS, exports and hardware access.
- Hardware passthrough requires explicit device access and the documented driver/qualification conditions. Server-side RTSP/ONVIF decoding requires `ffmpeg` in an extended image or a separate native deployment.
- Export byte limits apply to written data. The receiver can have buffered frames or a request in flight when the final write completes; shutdown releases queued frames and cancels outstanding requests. See [export accounting](https://github.com/fantuz/entropy-service/blob/v2.3.1/docs/client-output.md).
- The desktop GUI continues to run from the source archive with Python, GTK 4 and PyGObject. Download the [matching source ZIP](https://github.com/fantuz/entropy-service/archive/refs/tags/v2.3.1.zip) and select the matching CLI binaries in Options. Linux uses distribution packages; Windows uses MSYS2 UCRT64. CLI archives contain the two utilities and notices; GUI setup is described in the [desktop guide](https://github.com/fantuz/entropy-service/blob/v2.3.1/docs/desktop-gui.md).

Verify native downloads against the [SHA-256 manifest](https://github.com/fantuz/entropy-service/releases/download/v2.3.1/checksums.txt). Architecture-specific `releases/latest/download` aliases continue to follow the latest release.

After the tagged release and container publication complete, pull the matching images:

```sh
docker pull ghcr.io/fantuz/entropy-service:v2.3.1
docker pull ghcr.io/fantuz/entropy-client:v2.3.1
```

Docker selects the architecture automatically. Pin the image digest for an exact container build. Registry publication follows native release publication, so the two sets of downloads can become available at different times.

## Validation

Release publication waits for Go regression/race tests, lint/vet, reachable-vulnerability checks, bounded fuzzing, Chromium/Firefox tests, native Windows tests, packaged Windows execution, Linux systemd lifecycle checks, Linux/Windows endurance tests and the three-platform container checks/scans. Desktop GUI checks exercise native Linux and Windows rendering and owned-process behavior. Quantis tests distinguish header builds and simulated VM transport from physical device qualification.
