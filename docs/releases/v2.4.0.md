# Entropy Service v2.4.0 — native Windows Service support

The Windows x64 server can now run persistently under the Windows Service Control Manager without an open terminal or GUI. Linux, portable Windows console/GUI use, web/LAB features and client transports retain their existing behavior.

## Highlights

- **Native service lifecycle:** `entropy-server.exe service install/start/stop/status/uninstall`, automatic delayed startup, correctly quoted executable paths and explicit server startup options after `--`. Management checks the registered executable/account/arguments before controlling a service.
- **Dedicated identity and protected state:** the default service uses `NT SERVICE\EntropyServer`, without a password or LocalSystem privileges. Its protected state directory grants access only to the service account, Administrators and SYSTEM. Unsafe existing ACLs and paths through junctions/reparse points are rejected without automatic repair.
- **Explicit TLS provisioning:** `service install -self-signed` asks the service account to generate/reuse its own identity at startup. Keys retain the strict account-only ACL; Administrators/SYSTEM can read the public certificate and logs. Existing valid identities are reused; expired, partial, mismatched or unsafe pairs fail startup. No automatic certificate renewal or trust-store changes occur.
- **Shared lifecycle:** console and SCM operation share server initialization, readiness and cancellation. SCM Running is reported after listeners and reseeding start. Stop/Shutdown drains listeners and WebSockets and joins reseeding before exit. `/ready` remains the authority for seed freshness and generation availability.
- **Operational guidance:** the Windows Service guide ships in portable archives, covering setup, state, logs, TLS, upgrades and preserving uninstall. Windows GUI download guidance points to matching v2.3.1 source and binaries; the current v2.4.0 source archive also contains the same GUI controls.

## Quick start

Use an elevated PowerShell after extracting the verified Windows archive into an administrator-controlled permanent directory:

```powershell
cd 'C:\Program Files\Entropy Service'
.\entropy-server.exe service install -self-signed
.\entropy-server.exe service start
.\entropy-server.exe service status
```

The service defaults to loopback HTTP `127.0.0.1:8080`, HTTPS `127.0.0.1:8443` and state in `C:\ProgramData\entropy-service`. Installation registers automatic delayed startup; the explicit start command starts it now. Self-signed certificates require explicit client trust. The default local identity lasts seven days; monitor expiry and renew explicitly. For an initial HTTP-only test, install with `service install -- -enable-https=false` instead. No firewall rules are added.

See the [Windows Service guide](https://github.com/fantuz/entropy-service/blob/v2.4.0/docs/windows-service.md) for CA-issued identities, service names, logs and changing options. Stop before replacing an executable or uninstalling. Uninstall retains certificates, state and logs. Configure operator log retention; no automatic log rotation is provided.

## Compatibility and validation

This release adds native Windows x64 service operation. The existing Python/GTK GUI remains a separate source download with Linux distribution dependencies or Windows MSYS2 UCRT64; a bundled GUI installer and Authenticode signing are separate follow-ups. Windows ARM64 is not released. Existing Linux systemd packages and Linux amd64/arm64/ARMv7 containers remain supported.

Native Windows unit tests cover SCM readiness, interrogation, Stop/Shutdown joining, late readiness and failed startup. A required test installs the actual packaged executable as a uniquely named service, exercises verified HTTPS and private-key access protection, restart/certificate reuse, failed startup, unsafe-state rollback and preserving uninstall/reinstall. Full CI also covers Go race/regression/lint/vet and vulnerability checks, bounded fuzzing, Chromium/Firefox, Linux/Windows GTK, Linux systemd, Linux/Windows endurance and all three container platforms. Actual machine reboot and physical hardware qualification remain operator checks.
