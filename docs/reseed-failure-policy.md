# Reseed failure and freshness policy

The server defaults to **`-on-reseed-failure=stop`**. It refuses new serving-root
generation when a reseed fails or the last successful seed exceeds
`-max-reseed-age`. This is a serving policy, not a change to the DRBG's
cryptographic construction. `stop` pauses output; it does not terminate the
process or destroy the root needed for recovery.

## Configuration and observable states

```sh
./bin/entropy-server -device=/dev/urandom -require-device=true \
  -enable-https=false -http=127.0.0.1:8080 \
  -on-reseed-failure=stop -reseed-ms=15000 -max-reseed-age=60000
```

| Flag | Default | Effect |
| --- | --- | --- |
| `-on-reseed-failure` | `stop` | `stop` refuses generation on failure or staleness; `continue` explicitly retains the former availability-first behavior. |
| `-max-reseed-age` | `0`, resolved to `max(1000, 4 × reseed-ms)` milliseconds | Age of the last successful seed permitted for readiness and, in stop mode, generation. Factory effective default: 60000 ms. |
| `-reseed-ms` | `15000` | Retry interval in milliseconds; failures do not start overlapping reads. |

| Seed state | `/ready` | `stop` generation | `continue` generation |
| --- | --- | --- | --- |
| `fresh`: no unresolved error, age within limit | 200 | Allowed | Allowed |
| `failed`: unresolved read/reseed error, even if age is small | 503 | Refused | Permitted from existing state |
| `stale`: no reported error, but successful-seed age exceeds limit | 503 | Refused | Permitted from existing state |

A reported error takes precedence over `stale`. A successful complete source
read and successful root reseed clears the error, refreshes the clock and
advances the root epoch. Merely waiting, reading generated bytes, retrying a
request or changing readiness traffic does not restore freshness.

The seed-age default allows scheduling/read latency around the existing
15-second reseed interval. It is not a measured entropy rate or a proven
post-compromise recovery bound. Choose an age comfortably above expected
reseed latency; an age below the reseed interval can deliberately pause output
between otherwise successful reseeds.

## Client behavior and coverage

All twelve serving-root routes use the same admission gate, on both HTTP and
HTTPS: `/v1/data/random`, `/v1/data/test`, `/v1/meta/random`,
`/paroleparoleparole`, both `/v1/image/*` routes, `/v1/qr/random`, `/sound`,
and the `/stream`, `/bytes`, `/colors`, `/words` WebSockets.

- A denied HTTP request or new WebSocket handshake returns **503**,
  `Cache-Control: no-store`, and `Retry-After: 1`. The retry value is a hint,
  not a promise that the next reseed completes in one second. Back off retries.
- An HTTP binary transfer repeats the check at each bounded read (normally
  32 KiB). If freshness fails before the first body write, it returns 503.
  If a body has started, it ends short of the declared `Content-Length`;
  no textual error is appended to the random bytes. Clients must treat that
  incomplete sample as failed. The normal client HTTP fetch path rejects
  error statuses and failed/truncated body reads.
- Existing WebSockets check the serving root on every private-generator read.
  A separate notification/expiry watcher closes an unhealthy connection with
  **1013 (Try Again Later)**, even if its next frame tick is 60 seconds away
  or a socket writer is blocked. After recovery, clients establish a new
  connection. A socket already closed by this policy is not resurrected.
- Readiness, liveness, metrics, static pages, upload analysis and independently
  configured lab source bridges remain usable. These paths diagnose the
  server or consume other data rather than draw from its serving root.

The boundary is generation admission, not revocation of delivered data. A
read admitted while fresh may finish, and already generated/encoded bytes or
complete frames in user-space, kernel or peer buffers can still arrive after
a failure. Buffered images, QR codes, words or WAVs already generated from
healthy state may finish encoding/delivery. This is not an instantaneous
network-wide cutoff. HTTP request children remain private per request;
persistent WebSocket children still refresh on root epoch changes.

## Why these choices

**Fail closed by default.** Previously `/ready` could say 503 while all data
routes kept serving. Operators could reasonably mistake continued service
for a currently healthy source. Making the freshness contract enforceable
at the server removes dependence on every proxy/client polling readiness
correctly. It makes an availability tradeoff: a transient source error can
now interrupt consumers immediately. `continue` is an explicit escape hatch
for workloads that accept that tradeoff in the other direction.

**Two modes, with degradation visible in both.** A third `degrade` mode would
duplicate `continue`: readiness and failure metrics already report degraded
state while output continues. Neither mode conceals a source fault or silently
switches to an unrelated source.

**Use both errors and age.** An explicit error is actionable immediately;
waiting for a grace period would continue serving after a known failed
refresh. Conversely, a hung source may never return an error. Age expiry
denies further output independently of whether that read completes.

**Keep the process alive and recover automatically.** The original source and
root state remain available to the reseed loop, while `/live` stays healthy.
This avoids restart loops that repeat startup device selection/fallback and
obscure the cause. A later successful reseed restores admission, clears the
current error and lets persistent readers refresh their private state. The
operator does not need to restart after a recoverable source outage.

**Enforce below the HTTP layer as well.** A route-only check misses long
downloads and private child streams already open when failure occurs. Root
and descendant reads therefore share a serving-root freshness gate. Private
reads use a shared policy read lock, separate from the root cipher mutex,
so independent generators still run in parallel. Failure/reseed transitions
take the policy write lock; reads admitted before a transition may finish.
Neither source I/O nor network writes hold that policy lock. The existing
regression asserting that private bulk generation does not wait on the root
cipher mutex remains in force.

**Preserve cryptographic state and deterministic fixtures.** Refusing output
does not reseed with empty material, reset the byte budget, change the stream
algorithm, clear a failure prematurely or invent successful source input.
Failure and recovery use the existing SHA-512 reseed transition. Source
failure alone does not prove that old DRBG output has become predictable;
this feature enforces an operational freshness decision, not a new proof of
cryptographic security or hardware quality.

## Diagnostics and migration

Startup reports the effective policy and maximum age. Explicit `continue`
prints a warning. `/ready` and numbered health aliases add `seed_state`,
`on_reseed_failure` and `generation_allowed` fields. Existing fields remain.

Canonical `/metrics` and numbered compatibility exports add unique gauges:

| Metric | Meaning |
| --- | --- |
| `rng_generation_allowed` | 1 when the serving freshness policy allows output, otherwise 0; independent of capacity/admission budgets. |
| `rng_reseed_fail_closed` | 1 for `stop`, 0 for `continue`; the configured policy, not current health. |
| `rng_max_reseed_age_seconds` | Configured freshness-age threshold in seconds. |

Existing `rng_ready`, `rng_reseed_age_seconds` and
`rng_reseed_failures_total` retain their meanings. In `continue` mode,
`rng_ready=0` with `rng_generation_allowed=1` is intentional.

**Upgrade behavior changes:** configurations omitting the new flag now select
`stop`. To retain the earlier policy, explicitly add
`-on-reseed-failure=continue` before upgrading/restarting. Review hardware
read latency, age thresholds and client retry/reconnection behavior first.
The package still does not restart or enable services during installation.

## Remaining boundaries and verification

The gate does not interrupt an arbitrary kernel/device `Read`, cancel an
initial seed read before a root exists, reopen a failed device, or make that
worker join reliably at shutdown. Adding a timeout by abandoning a goroutine
would leave the original read alive, potentially leak workers, and allow
concurrent reads of one source. A source-specific cancellable I/O design is
separate work. The age gate prevents stale serving without claiming that fix.
Likewise, a defective source that returns enough predictable bytes still
looks fresh; online hardware health and min-entropy assessment remain separate.

Tests cover both normal backends (and the same gate in experimental builds),
root/child/nested-child refusal without buffer or counter changes, successful
recovery, explicit continue mode, all production generation routes, partial
HTTP transfers, all four WebSockets, idle socket expiry, resource cleanup,
blocked reseed input, notifications and concurrent failure/read/recovery.
Existing primitive vectors and seed/reseed fixtures verify that healthy
cryptographic behavior remains unchanged. Full regression/race/vet/lint,
experimental builds and packaging are validated by GitHub CI.
